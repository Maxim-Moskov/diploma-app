# diploma-app

Тестовое веб-приложение дипломного проекта: статическая страница на nginx, упакованная в контейнер, с автоматической сборкой и деплоем.

Часть итоговой работы курса Netology «DevOps-инженер». Общее описание проекта — в репозитории [diploma-devops](https://github.com/Maxim-Moskov/diploma-devops).

**Docker-образ:** [moskovmaxim/diploma-app](https://hub.docker.com/r/moskovmaxim/diploma-app)

## Приложение

Статическая страница на nginx, показывающая три параметра текущей сборки: порядковый номер, хеш коммита и время сборки. Значения вшиваются в образ на этапе сборки — плейсхолдеры `BUILD_VERSION`, `BUILD_COMMIT` и `BUILD_DATE` в `index.html` подменяются через `ARG` и `sed` в `Dockerfile`.

Смысл в том, чтобы деплой был **видимым**. Без этого после обновления страница выглядит идентично, и понять, новая там версия или старая, невозможно. А с хешем коммита на странице виден прямой путь от кода до работающего контейнера, и пайплайн может проверить это автоматически.

---

## Локальный запуск

```bash
docker build \
  --build-arg BUILD_VERSION=local \
  --build-arg BUILD_COMMIT=$(git rev-parse --short HEAD) \
  --build-arg BUILD_DATE="$(date -u '+%Y-%m-%d %H:%M') UTC" \
  -t moskovmaxim/diploma-app:local .

docker run -d --name diploma-app -p 8080:80 moskovmaxim/diploma-app:local
curl http://localhost:8080
```

Через Compose:

```bash
APP_IMAGE=moskovmaxim/diploma-app:latest docker compose up -d
```

Переменная `APP_IMAGE` имеет значение по умолчанию, поэтому команда работает и без неё. В пайплайне туда подставляется образ с тегом по хешу коммита.

## Образ

Базовый — `nginx:1.27-alpine`. Alpine-вариант весит около 50 МБ против 190 у обычного, а образ скачивается на ВМ при каждом деплое. Версия зафиксирована, а не `latest`: сборка должна быть воспроизводимой.

В образ встроен `HEALTHCHECK`, который каждые 30 секунд проверяет, что nginx отвечает. Docker Compose показывает результат в статусе контейнера:

```
NAME          IMAGE                             STATUS
diploma-app   moskovmaxim/diploma-app:8049535   Up 4 minutes (healthy)
```

Каждая сборка публикуется под двумя тегами: `latest` и короткий SHA коммита. Второй даёт однозначную привязку контейнера к коду и позволяет откатиться на любую прошлую версию.

## CI/CD

Пайплайн состоит из двух job'ов.

### `build` — при пуше в любую ветку

1. Получает исходный код
2. Формирует метаданные сборки (короткий SHA, дата)
3. Логинится в Docker Hub
4. Собирает образ и публикует под двумя тегами

### `deploy` — только при пуше в `main`

1. Разворачивает SSH-ключ из секрета
2. Копирует `compose.yaml` на сервер по `scp`
3. Запускает `docker compose up -d --pull always` с образом текущего коммита
4. Проверяет через `curl`, что страница отвечает и содержит хеш этого коммита

Условие `if: github.ref == 'refs/heads/main'` отделяет второй job от первого. Связь `needs: build` гарантирует, что деплой не начнётся, если сборка упала, и передаёт тег образа между job'ами.

Последний шаг — не формальность. Он защищает от ситуации «пайплайн зелёный, а приложение не работает»: если контейнер поднялся старый или nginx не отвечает, job покраснеет.

## Секреты

Настраиваются в Settings → Secrets and variables → Actions:

| Секрет | Содержимое |
|---|---|
| `DOCKERHUB_USERNAME` | логин Docker Hub |
| `DOCKERHUB_TOKEN` | Personal Access Token с правами Read & Write |
| `VM_HOST` | публичный IP виртуальной машины |
| `SSH_PRIVATE_KEY` | приватный SSH-ключ целиком, включая обе строки-рамки |

Пароль от аккаунта Docker Hub не используется — только отзываемый токен. SSH-ключ отдельный, создан специально для CI, личный ключ в секреты не попадает.

Имя пользователя на ВМ (`ubuntu`) в секреты не вынесено намеренно: оно не является тайной, а в открытом виде workflow читается понятнее.

## Проверка автоматического деплоя

```bash
# Изменить что-нибудь на странице
sed -i 's|старый текст|новый текст|' site/index.html
git commit -am "Проверка деплоя" && git push
```

Через две минуты страница по адресу ВМ обновится: номер сборки увеличится, хеш коммита сменится на новый.

---

## После пересоздания инфраструктуры

Публичный IP выдаётся динамически, поэтому после `terraform destroy` и повторного `apply` нужно обновить секрет `VM_HOST` и заново прописать ключ на новой машине (это делает Terraform через метаданные). Запустить деплой без изменений кода можно пустым коммитом:

```bash
git commit --allow-empty -m "redeploy" && git push
```
